# Andrej Karpathy：LLM 编程观察笔记

> 翻译自 Andrej Karpathy's observations on LLM coding pitfalls  
> 来源：[https://x.com/karpathy/status/2015883857489522876](https://x.com/karpathy/status/2015883857489522876)

---

这是我过去几周大量使用 Claude 编码后的一些零散笔记。

---

## 编码工作流

随着 LLM 编码能力的提升，和很多人一样，我的工作方式发生了快速变化：
从 11 月时大约 **80% 手写+自动补全 / 20% agent**，变成了 12 月的 **80% agent / 20% 手动修改与润色**。

也就是说，我现在基本是在**用英语写程序**——有点不好意思地用“文字”告诉 LLM 应该写什么代码。
这多少有点伤自尊，但这种以“大块代码操作”的方式来处理软件，实在太有用了。特别是当你逐渐适应、配置好、学会如何使用，并理解它的能力边界之后。

这是我近 **20 年编程生涯中最大的一次工作方式变革**，而且只用了几周时间就发生了。
我预计这种变化已经影响了相当比例（两位数百分比）的工程师，但大众对此的认知还停留在个位数。

## IDE / Agent 群 / 可靠性

目前来说，“不再需要 IDE”以及“agent 群体协作”的炒作都有点过头了。

模型仍然会犯错，如果你在写任何重要代码，**你必须像盯鹰一样盯着它**，最好在旁边开一个完整的 IDE。

错误类型已经发生变化：

- 不再是语法错误
- 而是**微妙的概念性错误**（类似一个略微粗心的初级工程师）

最常见的问题是：

- 模型会**替你做错误假设并一路执行下去**
- 不会主动澄清问题
- 不会暴露不一致
- 不会给出权衡
- 不会在该反对时反对
- 有点过于“讨好型”

在 plan 模式下会好一些，但仍然需要一种更轻量的 inline plan 模式。

另外：

- 它们倾向于**过度设计**
- 抽象膨胀
- 不清理死代码

经常会写出：

> 1000 行冗长、低效、脆弱的实现

这时你说：

> “能不能简单点？”

它会马上变成 100 行。

还有一个问题：

- 有时会修改/删除它不理解的代码或注释（即使与当前任务无关）

即便你在 `CLAUDE.md` 写了规则，这些问题仍然存在。

但即便如此，它仍然是**巨大的效率提升**，几乎无法想象再回到纯手写时代。

**TLDR：**
我当前的流程是：

- 左边：多个 Claude Code 会话（终端）
- 右边：IDE（查看 + 手动修改）

## 毅力（Tenacity）

看 agent 不断尝试解决问题非常有意思：

- 不会累
- 不会沮丧
- 会一直尝试

一个人可能早就放弃了，它却能坚持 30 分钟最终成功。

这是一种“接近 AGI 的体验”。

你会意识到：
**人类的工作瓶颈之一是体力/耐力，而 LLM 极大提升了这一点**

---

## 加速（Speedups）

很难衡量 LLM 带来的“加速”。

确实感觉更快，但更重要的是：

我做的事情**变多了**：

1. 以前不值得写的代码，现在会写
2. 以前能力不够的代码，现在也能做

所以不仅是加速，更像是**能力扩展**

---

## 杠杆（Leverage）

LLM 非常擅长“循环直到达成目标”。

这是最接近 AGI 的地方。

建议用法：

- 不要告诉它怎么做
- 给它**成功标准**

例如：

- 先写测试，再让它通过
- 接浏览器 MCP 让它自己操作
- 先写一个正确但笨的算法，再让它优化

从“命令式”转向“声明式”，可以获得更大的杠杆

---

## 乐趣（Fun）

没想到的是：

用 agent 编程**更有趣了**

原因：

- 枯燥的填空工作减少
- 剩下的是创造性部分

同时：

- 更少卡住
- 更有信心推进

不过也有人有相反感受：

LLM 会把工程师分成两类：

- 喜欢“写代码”的人
- 喜欢“构建东西”的人

---

## 能力退化（Atrophy）

已经开始注意到：

手写代码能力在退化

因为：

- 写代码（生成）和读代码（判断）是不同能力

即使写不出来，你仍然能很好地 review

## 总结（TLDR）

LLM agent（尤其是 Claude 和 Codex）在 **2025 年 12 月左右跨过了一个关键阈值**，引发了软件工程的“相变”。

现在的情况是：

- 智能能力已经明显领先
- 但其他部分还没跟上：
  - 工具集成
  - 工作流程
  - 组织方式
  - 普及速度

**2026 年将是一个高速变化的年份**
